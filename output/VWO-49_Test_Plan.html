1. Objective

Confirm that users can sign in to VWO with Single Sign-On (SSO) or a Passkey from the login page. The plan checks that:

  • both new buttons appear in the right place
  • successful sign-ins land on the dashboard
  • every failure shows a clear message
  • the flows work on supported browsers and devices and with every configured identity provider
  • the flows are secure (OAuth/SAML/WebAuthn, with no sensitive data exposed)
  • existing sign-in methods keep working

What “tested” means for VWO-49: all six acceptance criteria are verified, the seven test scenarios listed in the ticket are executed, and the ticket’s Definition of Done is met (deployed to staging, QA sign-off, no critical or high defects open, documentation updated).

2. Scope and inclusions

In scope

  • UI visibility: “Sign in using SSO” and “Sign in with Passkey” buttons, their labels, and their position below “Sign in with Google”.
  • SSO login flow: successful authentication and redirect to the dashboard, invalid credentials, and failed SSO authentication across all configured identity providers.
  • Passkey login flow: sign-in with a registered, verified passkey and redirect to the dashboard; the fallback or guidance message when no passkey is available; passkey authentication failure.
  • Error handling: messages for failed SSO, passkey failure, and an unsupported browser or device.
  • Compatibility: passkey login on supported browsers and devices only; SSO across configured identity providers.
  • Security: OAuth/SAML/WebAuthn protocols; no sensitive data in the UI or network logs.
  • UI responsiveness and accessibility of the new options (ticket scenario 7).
  • Regression: existing sign-in methods (email/password and “Sign in with Google”) that sit next to the new options.

Inclusions (test types applied)

  • Functional and UI testing of both new flows (positive, negative and boundary)
  • Error-handling and message validation
  • Compatibility testing across the agreed browser and device matrix
  • Security checks of the protocol use and data exposure
  • Responsiveness and accessibility checks
  • Smoke, sanity, regression and retesting
  • Exploratory and end-to-end testing (login page to dashboard)
  • Automated regression: repair and extend the existing n8n + Playwright run (TC-01 to TC-04)

Out of scope (as stated in VWO-49)

  • Passkey registration flow (covered in a separate story)
  • SSO provider configuration

Also out of scope unless the author adds them: performance/load targets, localisation, and dashboard features beyond confirming a successful landing. The ticket defines none of these (see G-13).

3. Requirement summary (from VWO-49)

User story

As a user, I want to log in using either Passkey or Single Sign-On (SSO), so that I can access my account more securely and conveniently without relying solely on email/password authentication.

The ticket says two new options, “Sign in using SSO” and “Sign in with Passkey”, have been added to the login page next to the existing authentication methods. They should work seamlessly and give a smooth user experience across supported environments.

Acceptance criteria

AC1 – UI visibility

  • GIVEN the user is on the login page, THEN “Sign in using SSO” and “Sign in with Passkey” are visible, AND they are displayed below the “Sign in with Google” option.

AC2 – SSO login flow

  • GIVEN the user clicks “Sign in using SSO”, WHEN valid SSO credentials are provided, THEN the user is authenticated and redirected to the dashboard, AND appropriate error messages are shown for invalid credentials.

AC3 – Passkey login flow

  • GIVEN the user clicks “Sign in with Passkey”, WHEN a registered passkey is available and verified, THEN the user is logged in AND redirected to the dashboard, AND if no passkey is available a fallback or guidance message is displayed.

AC4 – Error handling

  • Proper error messages for: failed SSO authentication; passkey authentication failure; unsupported browser/device for passkeys.

AC5 – Compatibility

  • Passkey login works on supported browsers/devices only. SSO works across all configured identity providers.

AC6 – Security

  • All authentication flows follow secure protocols (OAuth/SAML/WebAuthn). No sensitive data is exposed in the UI or network logs.

Test scenarios listed in the ticket

  1. Verify both new buttons are visible and correctly positioned
  2. Validate successful login via SSO
  3. Validate failed SSO login with incorrect credentials
  4. Validate successful login via Passkey
  5. Validate behaviour when no passkey is registered
  6. Validate behaviour on unsupported browsers/devices
  7. Verify UI responsiveness and accessibility

Definition of Done

  • Feature implemented and deployed to staging
  • All acceptance criteria met
  • QA sign-off completed
  • No critical or high defects open
  • Documentation updated

5. Test strategy

Step 1 – Design scenarios and test cases

Test scenarios (section 6) are derived from the acceptance criteria, the ticket’s own scenarios and the gaps in section 4. Test cases will be written after this plan is approved, using:

  • Equivalence class partitioning: valid and invalid SSO credentials; passkey registered or not; supported and unsupported browsers.
  • Boundary value analysis: zero, one or several registered passkeys; prompt timeout.
  • Decision table testing: sign-in method × identity provider × browser/device × account state.
  • State transition testing: login page → identity provider or passkey prompt → dashboard, or back to the login page with an error.
  • Use case testing: the end-to-end journeys for SSO and passkey users.
  • Error guessing and exploratory testing: cancel, retry, double-click and browser Back during each flow.

Test cases are prioritised P0 to P2. P0 covers the acceptance criteria and security; P1 covers secondary paths; P2 covers boundary cases.

Step 2 – Testing procedure for each build

  • Smoke test first: the login page loads and both new buttons are visible and clickable. If the smoke test fails, the build is rejected and in-depth testing waits for a stable build.
  • In-depth testing starts on a stable build, using the approved test cases. Several testers can cover different browsers and devices in parallel.
  • Defects are logged in JIRA and linked to VWO-49. An end-of-day status email goes to development management.
  • Test types: smoke and sanity · functional and UI · regression and retesting · usability · compatibility · security · accessibility.
  • Test cycles repeat until the exit criteria are met.

Step 3 – Best practices

  • Context-driven testing: focus on authentication risk; P0 covers sign-in success, failure handling and data exposure.
  • Shift-left testing: the questions in section 4 go to the author before the build, so expected results are agreed early.
  • Exploratory testing alongside scripted execution, as the triage comment also proposes (functional and non-functional testing, with manual techniques such as boundary values).
  • End-to-end flow testing: login page → identity provider or passkey → dashboard → logout.

Automation approach

The existing n8n + Playwright MCP run (TC-01 to TC-04) is the starting point. Before it is extended to the other P0 scenarios, the reason all four checks are blocked must be found and fixed (G-18). How to automate passkey prompts and identity-provider log-ins is still to be agreed TBC. Until then, those scenarios are executed manually.

11. Defect reporting procedure

  • What counts as a defect: any deviation from the VWO-49 acceptance criteria or the answers to section 4; any UX or accessibility issue on the new options; any technical error in the SSO or passkey flows; any exposure of sensitive data.
  • How to report: raise it in JIRA, linked to VWO-49, using the team template. Include environment and URL, browser/device and OS, identity provider or passkey authenticator used, steps to reproduce, expected vs actual result, and screenshots or a screen recording. Redact tokens and assertions from logs and HAR files.
  • Triage: assign severity and priority, then route to the right owner. Any exposure of credentials or tokens (AC6), and any failure of a P0 sign-in path, is raised as critical or high. These block the Definition of Done.
  • Owners (from the company defect process): Frontend POC for login-page UI and messages; Backend POC for SSO and WebAuthn authentication; DevOps POC for environment, identity-provider connectivity and deployment. Named owners for VWO-49 are TBC.
  • Communication: end-of-day status email listing the defects found that day; defect status reviewed in stand-up.
  • Metrics: defects found by severity, time to resolve, percentage fixed and retested, and pass rate of the P0 scenarios.
